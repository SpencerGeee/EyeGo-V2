# Four-scope audit — 2026-09-03

Runtime-proven pass over rider, driver, backend and admin. The bar was: nothing
is "done" unless it was executed against a live stack (Postgres 18 + Redis in
Docker, the API on :5020, the console on :4000), not merely read.

## What the baseline said

Before any change:

- **368/368 checks, 12/12 e2e suites green.**
- `tsc --noEmit` clean on rider, driver and admin.
- All 27 admin console pages render 200 server-side, including every dynamic
  route, against the full fixture set (61 trips, 227 bookings, 9 drivers, SOS,
  tickets, promotions, refunds).

So nothing had regressed. Everything below came from looking where the harness
does not: endpoints no suite calls, screens no check renders, and figures nobody
cross-checked against the domain that defines them.

## Fixed in this pass

### 1. A cash ride could be accepted by a driver who could not pay the commission

`eyego-api/src/modules/rides/rides.service.js` — `acceptRide()`

`assertCanAffordTrip` lives in `claimTrip`, whose comment states it sits there
because that is "the ONE verb every accept path routes through … so no fourth
path can skip it." `POST /rides/:id/accept` is the fourth path — and it is the
one the root-mounted offer sheet uses, i.e. the ordinary swipe-to-accept on a
one-rider cascade offer, the accept an average driver performs every day.

The driver swiped, drove to the pickup, and was refused at boarding with the
passenger standing there — precisely the scenario `wallet-commission.mjs` exists
to prevent. That suite passed throughout because it drives
`/driver/trips/:id/accept`, the path that always had the gate.

**Permanent check added**: `scripts/e2e/wallet-commission.mjs` — "the OTHER
accept verb refuses the broke driver too". Verified red-then-green: it now
returns `402 INSUFFICIENT_WALLET_FOR_TRIP`.

### 2. Two live settings the console could edit and nothing enforced

- `DRIVER_REQUIRED_WALLET_TO_GO_ONLINE_PESEWAS` — registered with the help text
  "A driver below this cannot go online", shipped to the app via
  `publicConfig()`, and read by nothing. `goOnline()`'s only balance test was a
  negative-balance (debt) check. An operator who set the floor to GH₵50 got
  exactly the behaviour they had at GH₵0. Now enforced in
  `drivers.service.js:goOnline`, from the **live** setting.
- `DRIVER_MIN_WITHDRAWAL_PESEWAS` — enforced in `wallet.service.js:withdraw`
  from `env`, the snapshot taken at process boot, while the app was told the
  current console value. Lowering the minimum changed what the app displayed and
  not what the endpoint accepted, so a driver was refused an amount the app had
  just called valid. Now reads the live setting.

> **Live consequence — read this one.** The go-online floor's configured value
> is **GH₵20** (`.env`, `.env.example`, and the `env.js` default). It has never
> actually been enforced, so drivers below GH₵20 have always been able to go
> online. Wiring it means that on the next deploy they cannot. The e2e harness
> stayed green because dev-mode auto-tops-up fixture drivers. If you do not want
> that floor live, set **Wallet required to go online → 0** in the settings
> console; the knob now genuinely controls the behaviour either way.

### 3. Admin counted booking rows everywhere it printed seats

Since an on-demand ride became one `Booking` row carrying `seats: partySize`, a
row count reports a party of four as one rider. The apps went through
`bookedSeats()`; the admin console and its API never did.

Fixed at source, so every display site inherits it:

- new `sumSeats()` in `eyego-api/src/utils/booking-status.js` — the CommonJS
  twin of `bookedSeats()`, with the same "how many people, not how many rows"
  rule, so the two cannot drift.
- `admin.service.js` — `getActiveTrips`, `getLiveDrivers`, `getUnassignedTrips`
  now sum seats into `_count.bookings` (consumers unchanged), and
  `getTripDetail`'s `occupancy.occupiedSeats` / `availableSeats` sum instead of
  counting rows.
- `apps/admin/.../trips/page.tsx` — the seat column summed `seats`; its type
  never declared the field, which is why it was counting rows. The API had been
  sending it all along.

This was wrong on the live board's "Seats", dispatch's "Riders", the "N riders
already booked" badge next to a reassignment control, and the trip detail's
"Seats taken N/M" — where the available figure invited an operator to sell seats
that do not exist.

### 4. A fabricated driver rating on the card riders choose from

`apps/rider/components/trip/stages/SelectStage.tsx` rendered
`(trip.driver?.rating ?? 4.8).toFixed(2)`.

`rating-integrity.service.js` deliberately returns `null` rather than a
flattering number for a driver with no countable ratings, and says in its own
comment that "callers decide how to present 'not rated'". This card decided to
present it as **4.80** — an earned-looking average, indistinguishable from a
real one, on the exact card a rider taps to pick a driver. Every brand-new
driver shipped with an invented score. Now renders "New".

### 5. Driver-side money units

- `apps/driver/app/(trip)/dispatch/[id].tsx` multiplied an already-pesewas nav
  param by 100, showing **GH₵450.00 for a GH₵4.50 ride** in the window before
  the real offer resolved — on the one screen whose whole job is the number the
  driver decides on. (Sole producer of that param sends pesewas.)
- `apps/driver/app/(tabs)/quests.tsx` — offline fallback quests stored cedis in
  a `*Pesewas` field, rendering "GH₵0.12" for a GH₵12.00 reward.

## Found and NOT fixed

Each verified by reading both sides. None is a regression; all predate this pass.

### Backend

1. **Refund remaining-amount check races outside its own transaction.**
   `refunds.service.js` reads `refundableAmount()` before opening
   `prisma.$transaction`, then validates against that pre-transaction figure.
   Every other money-debit path here uses a conditional `updateMany` guard. Two
   concurrent refunds on one booking can each pass validation and jointly refund
   more than the fare — the over-refund the file's own header calls out as the
   failure mode to design against.
2. **Two disjoint ledgers for one rider balance.** `RiderWalletTransaction` is
   written only by admin actions; every rider-initiated movement (top-up, P2P
   send, cancellation refund) writes `PaymentTransaction` instead, which is what
   `GET /wallet/transactions` reads. So an admin-issued refund changes the
   balance but never appears on the rider's statement — and `reconcile()`, the
   tool built to catch exactly that, sums only the ledger nobody writes to, so it
   reports drift for essentially every active rider.
3. **`DRIVER_MIN_WALLET_BALANCE_PESEWAS` is fully dead** — registered, editable,
   validated, read by nothing.

### Rider

4. **Four settings written, validated, and never read.** `speedAlerts`
   ("Notify you if your driver exceeds the speed limit" — no speed-monitoring
   code exists anywhere), `locationSharing` ("Share location with driver" —
   nothing consults it before transmitting GPS), plus analytics/crash opt-out
   and marketing notifications, neither of which any send path checks. Their
   siblings on the same two screens (`rideCheck`, `nightSafety`, `shareTrip`)
   *are* wired, so this is four specific fields, not a broken screen. Each is a
   safety or privacy promise the app does not keep; deciding between
   "implement it" and "remove the promise" is a product call, not a code one.

### Admin

5. **Refunds KPI tiles count the current page, not the result set** — "Awaiting
   the bank" and "Failed" are derived from the 25-row page array. The API
   returns real aggregates for total and amount but no pending/failed counts.
6. **CSV export truncation warning is plumbed and never shown.** The route
   forwards `x-eyego-truncated` (set when an export hits the 50,000-row cap)
   with a comment saying it exists so the page can warn — but the button is a
   plain `<a href>`, so nothing ever reads the header. A capped export looks
   like a complete one.
7. **`bulkDriverAction` is unreachable** — a working Server Action against a
   real endpoint, with no selection UI anywhere to call it.

### Driver

8. `(onboarding)/index.tsx` — a full 3-step wizard, registered as a screen, that
   nothing navigates to. Superseded by `/(profile)/vehicle` + `/documents`.
9. `detail/[id].tsx` reads `ratingReceived`, a field no backend service
   populates (per-trip ratings were removed for anonymity, by design). The
   section renders "No rating received for this trip yet" for every completed
   trip forever — a false negative rather than an honest "not shown".

## Coverage gaps the harness does not reach

The single largest: **the admin API has ~90 endpoints and the harness exercises
three of them, all refusal checks with no valid admin session.** It proves the
door refuses outsiders and proves nothing about what happens once an operator is
inside — including every moderation action, wallet adjustment, refund and
settings write.

Also untouched by any suite: `/v1/map-reports` (all 8 endpoints, the whole
"Improve Maps" feature), `/v1/contact` (call relay), `POST /cancellation/:id/cancel`
(the money-moving cancellation path — only its fee *quote* is tested), social
sign-in (`/auth/google`, `/auth/apple`), `/auth/logout`, the rider P2P
`/wallet/send`, driver `/wallet/withdraw`, driver SOS `/trips/:id/emergency`,
and the offline-passenger OTP verify step.

`scripts/e2e/README.md` is stale — it documents 11 suites; there are 12
(`release-surfaces.mjs` runs but is undocumented).
